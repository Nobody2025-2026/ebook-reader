# 真机读屏（屏幕阅读器）验收清单

> 状态：**待执行**。这是「打磨阶段」唯一没闭环的一项 —— 只能拿真机做。
> 完成标准：下面每一条都能勾上，勾不上的记在「发现问题」里回给开发。

## 为什么还要人工验一遍

我们已经跑过 **axe-core 自动审计**（9 个场景 0 违规），但那只能证明**结构合规**：
图片有 `alt`、按钮有可访问名称、对比度够。它证明不了

- 读屏**念的顺序**通不通顺（先念标题还是先念按钮？）；
- 念出来**像不像人话**（`aria-label` 存在 ≠ 念出来有意义）；
- 动态内容**会不会被播报**（toast 弹出来了，读屏软件不吭声等于没弹）；
- 划词浮层这种**临时浮层**，读屏用户根本够不着。

这四条只有真机能验。axe 的 0 违规 ≠ 读屏用户能用。

## 怎么开

| 平台 | 开启路径 | 常用手势 |
|---|---|---|
| iPhone | 设置 → 辅助功能 → 朗读内容 → **VoiceOver** → 开 | 单指左右滑 = 上下一个元素；双指上滑 = 从顶部连续朗读；双击 = 激活 |
| 安卓 | 设置 → 无障碍 → **TalkBack** → 开（不同 ROM 位置略有出入） | 同上；部分机型是单指上滑调出全局菜单 |

建议**开着读屏做完整流程**（导入 → 读书 → 加高亮 → 加笔记 → 导出），而不是只点几个按钮——
顺序问题只在完整流程里才暴露。

网页版入口：https://nobody2025-2026.github.io/ebook-reader/
（手机是**独立的本地书库**，得先在手机上导一本书）

## 五、临时浮层（已知高风险）

| # | 操作 | 预期 | 通过 |
|---|---|---|---|
| 23 | 选中一段文字后 | 读屏能**到达**浮层上的「加高亮 / 笔记 / 取消」等按钮 | ☐ |
| 24 | 浮层里的颜色选择 | 能听出颜色名（不是只念一个色块） | ☐ |
| 25 | 关掉浮层后 | 焦点回到正文，而不是消失 | ☐ |

> 这一块是真机读屏的公认难点：**浮层是异步出现的**，很多读屏软件不会自动把焦点挪过去，
> 也不播报它的出现。如果念不到，那是真问题，记下来（可能的解法是给浮层加
> `role="dialog"` + 焦点管理，或者至少 `aria-live` 播报一句"已选中，可加高亮"）。

## 发现问题怎么记

按这个格式回给开发，比"读屏不好用"有用得多：

```
平台：iPhone（iOS 版本）/ 安卓（机型 + ROM）
读屏：VoiceOver / TalkBack
页面：阅读页 → 顶栏
操作：单指右滑到「标记」按钮
预期：念「标记，按钮」
实际：念「加号 标记，按钮」（或者：没念、跳过去了、重复念了两次）
严重度：挡路 / 别扭 / 无所谓
```

## 已知风险点（先验这几条）

1. **浮层够不着**（第 23–25 条）：最可能出问题，优先验。
2. **`aria-valuetext` 的百分比**（第 12 条）：部分 TalkBack 版本不念 `aria-valuetext`，会退回念 0–1000 的原始值（代码里进度用的是 0–1000 的整数刻度）。如果听到「327」这种数字，就是这个。
3. **动态章节加载**（第 18 条）：连续滚动时新章是异步插进来的，读屏可能读不到或读重复。
4. **图片 alt**：自动补的是「《书名》封面」/「插图」；书里作者自己写的 `alt="image"` **我们没有覆盖**（形式合规、实质零信息），是否二次处理是待定的产品决策。
