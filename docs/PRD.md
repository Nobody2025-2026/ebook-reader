# 自制阅读器 · 产品设计文档

> 版本 v0.1（MVP 规划） · 2026-09-08

## 一、项目定位

**一句话目标：做一个能让人舒服地读完一本 EPUB 的阅读器。**

自己用的工具，不为发布、不为商业化。取舍时只问一件事：**这个功能是否直接服务于"把书读完"？是则留，否则延后。**

### 非目标（本轮明确不做）

PDF 阅读 · 账号与云同步 · 多设备 · TTS 朗读 · 字典翻译 · 笔记导出 · 书城与在线书源 · 移动端适配

> 说明：PDF 由既有的 PDF→EPUB 流水线负责转换成 EPUB 后导入，阅读器本身不背这个锅。

## 二、用户与场景

| 场景 | 期望 |
|---|---|
| 导入一批书 | 拖进去就能读，不用配置、不用注册 |
| 每天读一点 | 打开即回到上次位置，零操作成本 |
| 长时间阅读 | 字号行距主题可调，眼睛不累 |
| 读技术/学术书 | 目录随时跳转，方便回查章节 |

## 三、形态与技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 运行形态 | 纯 Web 应用 | 零后端，Mac / Windows 双机都能跑；日后可套 Tauri 转桌面端 |
| 框架 | Vite + React + TypeScript | 迭代快，类型安全 |
| EPUB 解析 | `epub.js` 或 `@lingo-reader/epub-parser` | 二选一，**待定**，见下方选型备注 |
| 存储 | IndexedDB | 存原始书文件 + 进度，容量够、无需后端 |
| 状态管理 | zustand | 轻量 |
| 排版 | CSS 变量 | 主题与排版参数实时切换 |
| 测试 | Vitest + 真实样本手工验收 | 见「七、验收标准」 |

**阅读模式：连续滚动**（不做分页翻页，规避窗口缩放重排的复杂度）。

### 选型备注：EPUB 解析库二选一（2026-09-08 实测）

| | `epub.js` 0.3.93 | `@lingo-reader/epub-parser` 0.4.6 |
|---|---|---|
| 最近更新 | 2023-09（基本停更） | 2026-04（活跃维护） |
| 定位 | 全栈方案：解析 + 渲染 + CFI 定位 + 分页 | 纯解析：元数据、目录、章节内容、图片资源 |
| 依赖 | 较老（jszip / xmldom 等） | 轻，TS 原生 |
| 与本方案契合度 | 偏向分页渲染，滚动模式要绕开 rendition | 契合连续滚动：拿到章节 HTML 自己渲染 |
| 代价 | 黑盒多，脏 EPUB 难调 | 进度定位要自己实现（章节 + 偏移） |

**倾向：`@lingo-reader/epub-parser` + 自己渲染。** 理由是 MVP 走连续滚动，epub.js 的分页 rendition 反而是负担；且《涛动周期论》这类脏 EPUB 需要能自己下场调解析细节。

**退路**：若自实现定位成本超预期，退回 `epub.js` 直接用 CFI。

> 更正：早期文档写作 `@lingo-reader/epub`，该包名不存在，正确名为 `@lingo-reader/epub-parser`。

## 五、页面结构

| 页面 | 职责 |
|---|---|
| 书库页 `/` | 展示全部书籍、导入入口、继续阅读、删除书籍 |
| 阅读页 `/read/:id` | 正文、目录抽屉、顶部工具条（返回 / 目录 / 排版 / 进度） |
| 排版面板 | 浮层，实时预览字号、行距、页边距、字体、主题 |

## 六、数据模型（IndexedDB）

```ts
Book       { id, title, author, cover?, format: 'epub'|'txt', file: Blob, addedAt }
Progress   { bookId, cfi: string, percent: number, chapterTitle, updatedAt }
Settings   { fontSize, lineHeight, pageMargin, fontFamily, theme }   // 全局单条
```

三个 object store：`books` / `progress` / `settings`。设置全局共用，不按书区分（MVP 阶段够用）。

## 九、桌面化预留（Tauri）

后期可能套 Tauri 转桌面应用。解析库选型对此**有利但非决定因素**——真正决定是否返工的是以下三条约束，MVP 阶段就要守住：

| # | 约束 | 说明 |
|---|---|---|
| 1 | 保持零后端、纯静态产物 | `dist/` 能被 Tauri 直接打包即可 |
| 2 | 路由用 HashRouter | Tauri 运行在 `tauri://` 协议下，BrowserRouter 的 pushState 会白屏（加壳第一大坑） |
| 3 | 抽象「书从哪来」 | 抽出 `BookSource` 接口：Web 实现 = 文件选择 + IndexedDB；桌面实现 = 文件对话框 + fs。解析层共用，不改 |

**解析层为何无痛**：`@lingo-reader/epub-parser` 提供 `node` / `browser` 双条件导出，API 同构（Node 传文件路径，浏览器传 `File`），加壳时只替换文件来源层。

**已知代价**：浏览器版资源以 blob URL 提供，多章连续加载需主动 `revokeObjectURL`，否则内存持续增长。已列入验收项。

## 十、真实样本实测（2026-09-08 · 《涛动周期论》）

用真实脏样本开刀后，纸上选型被修正了五处。**这一节是实测数据，不是推测。**

| 实测项 | 结果 | 对设计的影响 |
|---|---|---|
| 体积 / 打开耗时 | 70 MB，首次解析 1～8 秒 | 必须有加载态，不能点了没反应 |
| 章节 / 目录 | spine 28 章，TOC 26 条，标题能正常补全 | 目录方案可行 |
| 图片密度 | 13 / 28 章含图，单章最多 **45 张** | 图片懒加载是必需项，不是优化项 |
| 封面 | `getCoverImage()` 返回空串（manifest 里却有 `cover.jpg`） | 封面必须做兜底链，见下 |
| 元数据 | 标题是文件名 `140857_人生财富靠康波_周金涛`，语言标成 `en` | 标题需清洗；语言不可信 |

**封面兜底链**（已实现）：`getCoverImage()` → manifest 里找封面页 xhtml → `loadChapter` 后抠首个 `<img src>`。
其中藏着一个坑：manifest 的 `href` 是裸路径，而 `resolveHref()` 只认带 `epub:` 前缀的，必须两种都试。

**标题清洗**（已实现）：剥掉 z-library 的数字前缀，仅在整串无空格时把下划线还原成空格。

**Node 端性能陷阱**：`destroy()` 会逐个 `unlink` 落盘资源。在项目目录下删文件单个约 60ms，这本书会卡 20 秒以上。
对策：`openEpub()` 新增 `resourceSaveDir` 参数，Node 端一律指向系统临时目录（实测从 24 秒降到 14 毫秒）。浏览器端走 revoke blob URL，无此问题。

## 十一、待决问题

- 超过 10MB 的大部头加载性能是否需要预解析 / 懒加载（**实测 70MB 需 1～8 秒，已确定要加载态**）
- 封面缺失时的占位方案（**已有兜底链，仍可能拿不到，需占位图**）
- 滚动位置定位方案：CFI 还是「章节 + 字符偏移」（取决于解析库选型，见第三章）
- TXT 无目录结构，目录区如何处理（MVP 先隐藏）
