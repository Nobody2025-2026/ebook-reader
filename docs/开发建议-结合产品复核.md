## 二、工程优化点（务实、按 ROI 排序）

### 🟡 中优先级

**O-1 `epub.ts` 的 Node 内置模块被 externalize 进浏览器 bundle（真实隐患）**
- 证据：`epub.ts:382/400-403/522` 动态 `import('node:fs'|'node:os'|'node:path')`；构建警告 `Module "node:fs/promises" has been externalized for browser compatibility` + `[INEFFECTIVE_DYNAMIC_IMPORT]`。
- 问题：浏览器与 **Tauri webview 都没有 Node 运行时**，`node:fs` 在生产环境是 externalized stub（运行时 undefined）。这些路径若在生产被误调用会崩。
- 现状：注释（378 行）说"动态 import 是为不让浏览器 bundle 打进 Node 模块"——意图是浏览器走 ArrayBuffer、桌面端读本地文件走 fs。但 Tauri 桌面端 fs 应走 `@tauri-apps/plugin-fs`，**不是 `node:fs`**。
- 建议：
  1. 厘清这些 fs 路径的真实触发场景（Node 验收脚本？Tauri 读本地书？）；
  2. 若是 Node 脚本/测试用 → 抽到 `scripts/`（已存在 `scripts/*.mjs`），不要进前端 bundle；
  3. 若是 Tauri 桌面端读本地文件 → 改用 `@tauri-apps/plugin-fs`，删除 `node:fs` 依赖。
- 价值：消除"生产 bundle 带不可用 stub + 误调用崩风险"，并消掉两条构建警告。

### 🟢 低-中优先级（可做，但非瓶颈）

**O-2 `storage.ts` 的 get→map→set 重复模式**
- `addAnnotation`/`updateAnnotationNote`/`updateAnnotationColor`/`removeAnnotation`/`addBookmark`/`removeBookmark` 均为"读全数组→改→写全数组"，6+ 处同构。
- 建议：抽 `mutateList(bookId, key, fn)` 辅助，降出错面、提可测性。**但单书高亮/书签仅几十~几百条，性能非瓶颈，重构须配测试覆盖**，否则引入回归。

**O-3 `keys()` 全量扫描**
- `listProgress`/`listStats` 每次扫全部 IDB key 再 filter；书多时略浪费。可维护索引 key 或仅遍历 meta。量小，低优先。

**O-4 首屏 bundle 拆 chunk（润色）**
- JS 420KB 主要来自 EPUB 解析库（@lingo-reader/epub-parser + sax）。可 `import()` 动态拆 chunk，进书时才加载解析库，首屏不背 134KB。
- 首屏 gzip 134KB 对阅读器**可接受**，属优化非修复，低优先。
