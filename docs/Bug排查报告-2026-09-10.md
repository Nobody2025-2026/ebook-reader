## 一、正文图片全部不显示（真 bug，已定位到根因）

### 现象
EPUB 正文里的插图**一张都不显示**，位置留白（说明 `<img>` 元素在、尺寸占位在，就是没图）。

### 证据（真浏览器实测）
用无头 Chromium 导入《涛动周期论》并滚动到含图章节，逐张检查：

| 指标 | 实测值 |
| --- | --- |
| `<img>` 总数 | 46 |
| `src` 形态 | 全部 `blob:http://127.0.0.1:5180/<uuid>` |
| `naturalWidth` | **0（全部）** |
| `displayWidth` | 680（占位宽度正常） |
| 直接 `fetch(src)` | `content-type: image/jpeg`，**byteLength = 0** |
| `new Image().src = blob` | **decode error** |

**关键结论**：不是"死链"（fetch 能返回 200），而是 **blob 内容为空**（0 字节）。
截图确认：图注文字（"图1-21 1866—2014年太阳黑子…"）下方是大片空白。

### 根因
解析库 `@lingo-reader/epub-parser` 的**资源缓存生命周期缺陷**：

1. 库用**模块级全局对象** `imageRecord` 暂存解压出的图片字节，用**模块级全局 Map** `browserUrlCache` 缓存生成的 blob URL。
2. `destroy()` 会做两件破坏性操作：
   ```js
   destroy() {
     this.savedResourcePath.forEach((fp) => { if (existsSync(fp)) unlink(fp) })  // 清空全局 imageRecord
     revokeBlobUrls()  // 撤销全局所有 blob URL 并 clear
   }
   ```
3. 本项目里 `openEpub()` 会被**多次调用**：导入时一次、进阅读页一次、后台补封面又一次。**每次用完都会 `destroy()`**。
4. 任意一次 `destroy()` 都会把**全局** `imageRecord` 清空 —— 而阅读页里已经渲染的 `<img src="blob:…">` 依赖的字节也随之消失。后续 `getResourceUrl` 再读就是 `undefined` → `new Uint8Array(undefined)` → **0 字节 blob**。

**实测佐证**：在库的 `readFileSync` 里打探针，读到的是 `null`（未命中），而**写入时的 key 与读取时的 key 完全一致**（如 `/images/EPUB_images_cover.jpg`）—— 说明不是路径算错，是**条目被删了**。

### 为什么之前没测出来
`tests/real-book.test.ts` 跑在 **Node 环境**：Node 版走真实文件系统路径（`resourceSaveDir` 指向 `mkdtemp` 临时目录），**不涉及 `imageRecord` / blob 缓存**，所以永远测不出这个浏览器专属问题。

### 修复方向（建议）
**绕开库的 blob 机制，图片改为自己解 zip 转 data URL**（与封面那条已验证的路径同源）：
- `weights.ts` 里已有 `unzipSync` / `findEntry`（找 OPF 路径与 zip 条目的工具）。
- 解析层（`epub.ts`）在 `loadChapter` 之后，把 html 里指向本地资源的 `src` 换成 `data:image/...;base64,...`。
- 需要建立"章节内第 N 个 `<img>` ↔ manifest 图片 href"的映射（manifest 里 408 张图的 href 形如 `EPUB/images/image_000.jpg`，可直接从 zip 命中）。
- 代价：data URL 比 blob 占内存（base64 膨胀 33%），但**生命周期完全可控**，且能配 `loading="lazy"` + 图片懒加载策略（或做 ImageBitmap 缓存）。
- 备选：不改结构，改为**保证 `destroy()` 不在阅读期间被调用**（App 侧收敛 `openEpub` 次数）。但库的全局状态本身就是设计缺陷，改起来更脆。

### 优先级
**P0** —— 这是"能不能读图"的功能性缺陷，直接违反 MVP 目标。多图的书（本书 13/28 章含图）体验断崖。

## 二、《巴菲特致股东的信》无法导入书库（真 bug，已定位到根因）

### 现象
导入该书时书库无任何反应/报错，书加不进书架。

### 证据
在 vitest（Node）环境直接 `openEpub` 该书，抛出：

```
Error: Within the package there may be one guide element, containing one or more reference elements.
    at parseGuide (.../epub-parser/dist/index.node.mjs:467:11)
    at EpubFile.parseRootFile (...:925:20)
```

检查该书的 `content.opf`：

```xml
<guide>
  </guide>
```

**`<guide>` 元素存在但为空**（没有 `<reference>` 子元素）。

### 根因
解析库 `parseGuide()` 的健壮性缺陷：

```js
function parseGuide(guideAST, baseDir) {
  const references = guideAST.reference
  if (!references) {
    throw new Error('Within the package there may be one guide element, ...')  // ← 直接抛
  }
  ...
}
```

**空 `<guide>` 是完全合法的 EPUB 2 结构**（EPUB 3 已废弃 guide）。库把"没有 reference"当成致命错误抛出，导致**整本书打不开**。这是 calibre 2.40 转换产物的常见形态。

### 修复方向（建议）
本层兜底，别让解析库的异常决定书的生死：
- **方案 A（推荐）**：`openEpub()` 里对 `initEpubFile` 做异常兜底——捕获该特定错误后，**绕过 guide 解析**重试。但库没有暴露此开关，实现上要么改库（不现实），要么……
- **方案 B（务实）**：**导入前预处理 OPF**——若 `<guide>` 为空标签，先解 zip、把空 guide 剔除或补一个合法 `<reference>`，再交给解析库。改动集中在 `epub.ts` 的解析入口。
- **方案 C**：`<guide>` 为空时降级——用一个自实现的轻量解析分支处理这本书（成本高，不推荐）。

**推荐 B**：解 zip → 文本替换 `<guide>\s*</guide>` 为合法结构（或删掉）→ 重新打包字节 → 交给库。复用已有的 `unzipSync` / `findOpfPath`，改动可控。

### 优先级
**P1** —— 影响特定来源（calibre 转换、空 guide）的书的可用性。不是所有书都中招，但中招即完全不可用。

## 三、翻页卡在某一页，只能上翻不能下滚（真 bug，已定位到根因）

### 现象（来自录屏 `录屏2026-09-10 13.21.21.mov`）
书名《笔记的方法》，进度 **5.6% → 5.7%** 之间。鼠标滚轮**持续下滚，正文纹丝不动**；上翻正常。**下滚一段距离后有概率恢复，又有概率继续卡住**。

录屏已读出：9.9 秒 / 3994×2196 / 60fps，逐帧确认正文区无任何滚动位移。

### 定位
5.6% 按字数权重落在 **chapter 4「自序 记笔记，是为了增援未来的自己」**（该章权重 5451，全书 136586，区间 3.86%–7.85%）。
本书共 24 章，其中 **chapter 22、23 权重为 0**（空章）。

### 根因：章节加载链被"丢事件"永久中断
`Reader.tsx` 的 `loadChapter` 有一个**会丢弃请求**的守卫：

```js
const loadChapter = useCallback(async (index) => {
  if (!book || !chapters.length) return
  if (index < 0 || index >= chapters.length) return
  if (loadedIdxRef.current.has(index) || loadingRef.current) return   // ← 正在加载就丢弃
  loadingRef.current = true
  try {
    const { html, css } = await book.loadChapter(chapters[index].id)
    loadedIdxRef.current.add(index)   // ← 注意：await 之后才登记
    ...
  } finally {
    loadingRef.current = false
  }
}, [])
```

配合 `IntersectionObserver`（**只在交叉状态"变化"时回调**）：

```js
useEffect(() => {
  const observer = new IntersectionObserver(
    (entries) => {
      if (entries.some((e) => e.isIntersecting)) {
        const next = Math.max(...loadedIdxRef.current) + 1
        void loadChapter(next)          // ← 若此刻 loadingRef=true，被静默丢弃
      }
    },
    { root: container, rootMargin: '600px' },
  )
  observer.observe(sentinel)
  return () => observer.disconnect()    // ← 每次 loaded 变化都重建
}, [loaded, loadChapter])
```

**卡死链路**：
1. sentinel 进入视口（含 600px 预加载边距）→ 回调 → `loadChapter(next)` → `loadingRef = true`
2. 加载尚未结束，**sentinel 仍在视口内**（快滚 / 内容还在渲染 / 新章节撑高改变了布局）
3. `loaded` 变化 → effect 清理并**重建 observer**（`disconnect()` + 重新 `observe()`）
4. 重建后 sentinel **仍在视口内 = 交叉状态没变化** → 浏览器**不再补发回调**（IntersectionObserver 的语义）
5. 若此时那一次 `loadChapter` 又因 `loadingRef.current === true` 被丢弃 → **没有任何重试机制** → 加载链**永久中断**
6. 表现：后面章节永远不出现 → 容器高度不再增长 → **滚到底就卡住**
7. 把 sentinel 滚出视口（上翻）再滚回来（下滚）→ 交叉状态**变化** → 回调重新触发 → **"有概率恢复"**

**为什么是"卡在某一页"而不是"一直卡"**：竞态窗口很窄（只在"加载中 + observer 重建 + sentinel 未离开视口"三者同时成立时触发），所以**时好时坏**，与主上大人描述完全吻合。

### 修复方向（建议）
不要依赖"交叉状态变化"这一次性事件来驱动加载：
- **方案 A（推荐）**：把"是否需要加载下一章"改为**可重入的检查函数**，在 `onScroll`（已经存在，`handleScroll`）里顺带判断"距底部是否小于阈值"，是就尝试加载。滚动事件是连续源的，天然自愈，不会丢事件。
- **方案 B**：`loadChapter` 的守卫改为"**排队**"而非"丢弃"——`loadingRef` 忙时记下待加载 index，当前加载完成后自动续上。
- **方案 C**：`IntersectionObserver` 回调里若发现被丢弃，用 `setTimeout` 重试（治标，不推荐）。
- **建议 A + B 一起**：`onScroll` 阈值触发（主）+ 排队补加载（兜底），双保险。
- 另建议：给"已在视口内但未加载"加一个 `requestAnimationFrame` 轮询兜底，彻底摆脱 Observer 语义陷阱。

### 优先级
**P0** —— 直接破坏"读完一本书"的核心体验，且用户无法自行绕过（只能反复上下滚碰运气）。

## 四、共性总结（给后续改动提个醒）

1. **解析库的全局状态是雷区**：`imageRecord` / `browserUrlCache` 都是模块级全局，跨实例互相踩。凡是跟"库的资源生命周期"打交道的功能，都要警惕。
2. **Node 测试测不出浏览器专属 bug**：blob / IntersectionObserver / 布局时序这三样，Node 环境全是盲区。**建议补一个 Playwright 冒烟测试**（真浏览器跑"导入 → 翻页 → 图片可见"），把它纳入回归。
3. **`destroy()` 的破坏性被低估**：库的 destroy 不止释放自己，还清全局。以后调用前先想清楚"现在还有谁在用"。
4. **空元素/空集合是脏书的常态**：`<guide>` 空、`<spine>` 空、权重全 0 都见过。解析入口要"能兜就兜，绝不因为一个可选结构缺失就整本报废"。
